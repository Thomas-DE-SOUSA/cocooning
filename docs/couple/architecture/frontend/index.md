# Front de la PWA

Comment la PWA `apps/couple/web` parle à l'API, et ce que porte chaque package front. Les règles de code front sont dans `_knowledge/core-frontend.md`.

| `src/app/sw.ts` | Service worker Serwist, compilé en `public/sw.js` : précache du build ; les pages et leurs charges RSC passent toujours par le réseau (`isPageRequest`, `src/app/sw-page-request.ts`), jamais par un cache, pour qu'aucune donnée du couple ne reste lisible après une déconnexion ou hors ligne ([décision 0036](../../decisions/frontend/0036-lecture-des-donnees-par-la-page-serveur.md)) ; les photos du couple (`WebRouterEnum.INSTANT_PHOTO_FILE`) aussi (`isInstantPhotoRequest`), avant la route `/api/` de `defaultCache` qui les garderait ; le reste (scripts, styles, images) suit `defaultCache` ; à l'activation, les caches de pages d'une version précédente sont supprimés ; repli vers `WebRouterEnum.OFFLINE` quand une page ne charge pas ; nouvelle version active sans attendre (`skipWaiting`, `clientsClaim`) ; pas de rechargement au retour du réseau (`reloadOnOnline: false`, `next.config.ts`) ; notifications Web Push : l'écouteur `push` fait de la charge `{ kind }` la phrase française et l'écran à ouvrir (`pushNotificationOf`, `src/app/sw-push-notification.ts`, phrases dans `src/i18n/locales/fr/messaging/push.json`), un genre inconnu ou une charge illisible montre « Cocooning a du nouveau » ; un toucher sur la notification ramène une fenêtre ouverte de l'app sur cet écran, ou en ouvre une (`openAppAt`, `src/app/sw-notification-click.ts`) |

## Le chemin d'un appel

Exemple réel : la connexion, dans `apps/couple/web/src/modules/authentication/` ([décision 0035](../../decisions/frontend/0035-formulaires-de-la-pwa.md)).

1. La vue (`ui/views/sign-in-form.view.tsx`) reçoit le formulaire react-hook-form de `hooks/use-sign-in-form.ts`, qui valide par `createSignInFormSchema(t)` : une erreur s'affiche sous son champ (`Field`, `FieldError`).
2. Le container (`ui/containers/sign-in.container.tsx`) branche `hooks/use-sign-in.ts` sur la gateway du module (`gateways/index.ts`). Le hook reçoit la gateway et ses callbacks en paramètres, jamais l'action (règle 21 de `_knowledge/core-frontend.md`).
3. La gateway `ServerActionAuthenticationCommandGateway` appelle la server action ; le navigateur ne parle jamais directement à l'API. Un appel qui rejette devient une `ApiError` `NETWORK_ERROR` (`runServerAction`, `src/shared/application/server-action/`). Si la page date d'avant un déploiement, l'action n'existe plus sur le serveur : la page se recharge sur la nouvelle version.
4. La server action (`actions/authentication-sign-in.action.ts`) délègue à `services/sign-in-session.service.ts` : il revalide l'entrée par le même schéma, appelle `SignInUseCase` de `couple-client-business-logic`, construit par `createAuthenticationModule(API_URL, API_TIMEOUT_MS, getSessionToken)` (`services/authentication-module.factory.ts`).
5. Le use case appelle son port ; la gateway `ApiAuthenticationGateway` de `couple-client-infrastructure` vérifie la requête par le schéma du contrat, l'envoie par `httpRequest`, puis vérifie la réponse par `parseResponse`. Aucun appel ne transmet l'adresse IP ni le User-Agent du navigateur ([décision 0043](../../decisions/authentication/0043-le-tailnet-borne-les-essais-de-connexion.md)).
6. Tout revient en `Result` : aucune couche ne lève d'exception. Après un succès, le container navigue vers `WebRouterEnum.HOME`.

## Le chemin d'une lecture

Exemple réel : la mise en couple, dans `apps/couple/web/src/modules/pairing/` ([décision 0036](../../decisions/frontend/0036-lecture-des-donnees-par-la-page-serveur.md)).

1. La page `src/app/pairing/page.tsx` (rendue à chaque requête, `dynamic = 'force-dynamic'`) appelle `loadMyCouple()`, qui exécute `GetMyCoupleUseCase` du module construit par `pairingModule()`.
2. La fabrique reçoit `getSessionToken` (`src/shared/application/session/`) sans l'appeler. `ApiPairingGateway` le lit à l'appel et renvoie la session à l'API dans l'en-tête `Cookie`.
3. Le presenter `presentPairingPage` décide : `UNAUTHORIZED` renvoie vers `WebRouterEnum.ACCOUNT_SIGN_IN`, un couple formé vers `WebRouterEnum.HOME`, sinon l'écran « sans couple », « code d'invitation » ou « indisponible ». L'accueil suit `resolveHomeDestination`.
4. Une action (créer le couple, saisir le code de l'autre, nouveau code, annuler le couple) passe par une server action qui rend `Result<null, ApiError>`, puis le container appelle `router.refresh()` : la page relit le couple. Une seule action tourne à la fois. Un refus `UNAUTHORIZED` renvoie vers la connexion, un `CONFLICT` ou un `NOT_FOUND` relit l'écran. L'écran se relit aussi quand la PWA revient au premier plan et sur « Actualiser ». Pendant la lecture, `src/app/pairing/loading.tsx` montre des `Skeleton`.

L'accueil suit le même chemin pour les notes (`apps/couple/web/src/modules/notes/`, [décision 0053](../../decisions/frontend/0053-ecran-des-espaces-et-des-dossiers.md)) : `src/app/(tabs)/(home)/page.tsx` vérifie d'abord le couple (`resolveHomeDestination`), puis `loadNotesHome()` lit en parallèle, par `notesModule()`, les deux espaces (`GET /note-spaces`) et les cinq notes modifiées en dernier (`GET /notes`, première page de `RECENT_NOTES_COUNT` notes). `presentNotesPage` renvoie vers la connexion sur `UNAUTHORIZED`, vers `/pairing` sur `NOTE_COUPLE_NOT_PAIRED`, et met la date de modification à l'heure de Paris. L'écran montre « Partagé » (« Vu par vous deux ») et « Privé » (« Rien que pour toi »), chacun avec son nombre de dossiers et de notes, puis « Modifiées récemment » : chaque note, son espace et sa dernière modification. L'accueil n'a pas de « + » : une note se crée dans un espace. Les actions réservées à la propriétaire ne s'affichent que si l'API a répondu `isOwner`. Un refus `NOT_FOUND`, `FORBIDDEN` ou `CONFLICT` relit l'écran : l'autre partenaire a pu déplacer, rendre privée ou supprimer une note entre-temps.

Un espace des notes et chacun de ses dossiers ont leur écran, `src/app/(tabs)/spaces/[space]/page.tsx` (`WebRouterEnum.NOTE_SPACE`, le dossier dans le paramètre `folderId`, [décision 0053](../../decisions/frontend/0053-ecran-des-espaces-et-des-dossiers.md)). `presentNoteSpaceQuery` lit l'adresse : un espace inconnu renvoie à l'accueil, un identifiant de dossier invalide à la racine de l'espace. La page lit en parallèle le couple et `GET /note-spaces/:space/contents` (`loadNoteSpaceContents()`), applique les renvois de l'accueil, puis `presentNoteSpacePage` : connexion sur `UNAUTHORIZED`, `/pairing` sur `NOTE_COUPLE_NOT_PAIRED`, racine de l'espace pour un dossier disparu, privé de l'autre ou d'un autre espace. L'écran montre un retour vers le niveau du dessus (l'accueil au-dessus d'un espace), tiré du chemin que rend l'API, le nom du lieu, puis ses dossiers, chacun avec ce qu'il contient (« 1 dossier · 4 notes »), et ses notes.

Un bouton « + » flottant, au-dessus de la barre d'onglets, ouvre un petit menu « Nouvelle note » ou « Nouveau dossier » (Escape ou un appui ailleurs le ferme) ; chacun ouvre une feuille qui monte du bas, qui nomme le lieu de la création et n'a qu'un champ, validé sous le champ (`createNoteTitleFormSchema(t)`, `createFolderNameFormSchema(t)`) ; la note ou le dossier se crée à l'endroit affiché (R13). Toutes les commandes de l'écran passent par cette même feuille : une server action revalide le nom et le lieu, un succès ferme la feuille et relit la page par `router.refresh()`, un refus affiche un toast puis suit le chemin des notes. « Nouveau dossier » propose « Classique » ou « IA » (R17) : pour un dossier IA, « Proposer avec l'IA » demande à l'API le sujet et la fiche type d'après le nom (une server action, sans recherche ni plafond), le couple les corrige (une case se retire par sa croix, s'ajoute par un petit champ) puis crée le dossier ; si l'IA ne répond pas, un toast le dit et les champs se remplissent à la main. Dans un dossier IA, « Nouveau dossier » ne demande que le nom : le sous-dossier garde la fiche du dossier IA (R18). Un dossier IA porte l'étiquette « IA » dans les listes.

L'écran d'un dossier IA est le même, avec le contexte de fiche que rend l'API (`cardContext`) : « IA » à côté du nom, le sujet dessous, ou « Garde la fiche de « Restaurants » » dans un sous-dossier. En haut, une boîte d'ajout : le nom tapé (« Chez Paul ») part par une server action, la note existe tout de suite avec sa fiche « en recherche » (R19, R20), puis la page se relit. Chaque note du dossier montre sous son nom les deux premières valeurs de sa fiche, ou son état : « en recherche… » avec une barre qui pulse, « Lequel ? », « recherche impossible », « plafond du jour atteint, réessaie demain ». Sous la boîte d'ajout, chaque fiche en doute montre « Lequel ? » et ses candidats (au plus trois, le nom puis ce qui les distingue) : un toucher choisit, « Aucun de ceux-là » ouvre un champ « Précise (ville, quartier…) » qui relance la recherche ; les deux passent par une server action qui revalide l'identifiant de la note, la position ou la précision. Tant qu'une fiche est en recherche, l'écran se relit toutes les quatre secondes (`router.refresh()`), jamais quand la PWA est cachée. Les messages des fiches vivent dans le namespace `notes/card` ; un 503 de l'IA ou de la recherche arrive en `UNKNOWN` avec son `backendCode` et se traduit « L'IA ne répond pas » ou « La recherche ne répond pas ».

Le « ⋯ » d'un dossier ouvre la même feuille sur ses actions : « Renommer » montre son nom à modifier, « Supprimer le dossier » demande une confirmation qui dit ce qui remonte et où (« Ses 4 notes et son dossier remontent dans « Partagé ». Aucune note n'est supprimée. », R16). Les deux partenaires agissent sur un dossier de « Partagé » ; un dossier de « Privé » n'est montré qu'à son propriétaire, la PWA ne vérifie donc rien de plus. Sur un dossier IA, ou un sous-dossier de son arbre, la feuille propose aussi « Modifier la fiche » : le sujet et les cases, corrigés comme à la création, partent par une server action ; les fiches de l'arbre suivent la nouvelle fiche type (R17, R22).

Le « ⋯ » d'une note propose « Déplacer » et, sur une note dont l'API a répondu `isOwner`, « Supprimer la note », confirmée par « Supprimer pour nous deux » (R7). « Déplacer », sur une note comme sur un dossier, change la feuille en sélecteur : il part du niveau que la page a lu, sans nouvelle lecture, puis chaque lieu ouvert (un dossier, le retour au-dessus, l'autre espace) passe par une server action qui lit `GET /note-spaces/:space/contents`. La note de sa propriétaire peut aller dans les deux espaces, celle de l'autre reste dans « Partagé » (R5, R11), un dossier reste dans son espace et ne se montre pas lui-même, ce qui rend ses sous-dossiers inaccessibles (R15). « Déplacer ici, dans « Maison » » attend tant que le lieu montré est celui de l'élément. L'API reste seule juge : un refus (`FOLDER_MOVE_INVALID`, `FOLDER_SPACE_MISMATCH`, `NOTE_RESERVED_TO_OWNER`) s'affiche en toast.

L'onglet « Agenda » (`src/app/(tabs)/agenda/page.tsx`, module `apps/couple/web/src/modules/agenda/`) suit le même chemin ([décision 0048](../../decisions/frontend/0048-calendrier-react-day-picker.md)). Le jour choisi et le mois affiché sont des paramètres de l'adresse, `?day=YYYY-MM-DD&month=YYYY-MM`, lus par `presentAgendaQuery` (absents ou invalides : aujourd'hui à Paris et son mois). La page lit en parallèle le couple par `loadMyCouple()` et, par `loadCalendarEvents()`, les événements de la grille visible (du lundi qui précède le 1er au dimanche qui suit le dernier jour, `presentMonthGridRange`), plus ceux du jour choisi quand il n'est pas dans cette grille. Les renvois sont ceux de l'accueil (`resolveHomeDestination`), puis `presentAgendaPage` renvoie vers la connexion sur `UNAUTHORIZED` et vers `/pairing` sur `CALENDAR_EVENT_COUPLE_NOT_PAIRED`. Elle lit dans le même temps les étiquettes du couple (`loadCalendarLabels()`, `GET /calendar-labels`) : un refus de cette lecture rend l'écran indisponible comme celui des événements. Il calcule les points sous chaque jour (trois au plus, à la couleur de l'étiquette, neutres sans étiquette, anneau pour un événement privé, R13) et, pour chaque jour de la grille, son libellé et ses événements (`presentAgendaDays`) : chaque carte porte à gauche une barre de la couleur de son étiquette, et sous son titre la pastille « Moi », « Toi », « Nous deux » ou « Rien que pour moi » (R11), puis le nom de l'étiquette ou « Sans étiquette ». Toucher un jour l'affiche depuis ces données, sans le serveur : `useAgendaScreen` garde le jour choisi dans l'état du container et met l'adresse à jour par `window.history.replaceState`. « Aujourd'hui », dans l'en-tête posé par le container, choisit aujourd'hui de la même façon quand son mois est affiché. Changer de mois, ou revenir à « Aujourd'hui » depuis un autre mois, navigue vers la nouvelle adresse et la page relit l'agenda ; la page donne au container la clé `jour/mois` lue, si bien qu'une nouvelle lecture repart de son propre jour choisi.

Les écritures de l'agenda passent par une feuille qui monte du bas (`Drawer` du design system). Le bouton flottant « + », au-dessus de la barre d'onglets, l'ouvre pour un nouvel événement le jour choisi ; toucher un événement de la liste l'ouvre en modification. Le formulaire suit `createCalendarEventFormSchema(t)` (erreurs sous les champs) ; le jour et les heures sont des champs natifs qui ouvrent les sélecteurs du téléphone et rendent des chaînes `YYYY-MM-DD` et `HH:MM` ([décision 0047](../../decisions/agenda/0047-moments-de-l-agenda-en-heure-de-paris.md)). Sous les heures, « Pour qui » se choisit en trois boutons, « Moi », « Toi » ou « Nous deux » (« Nous deux » à la création, R11). La ligne « Rien que pour moi » donne la visibilité à la création (R3) et rend l'événement « pour moi » ; à la création, choisir « Toi » ou « Nous deux » l'éteint ; en modification, seul l'auteur la voit, et « Enregistrer » envoie la modification si un détail a changé, puis le partage ou le passage en privé si la visibilité a changé (R8). Puis « Étiquette (facultative) » : une puce par étiquette du couple, la puce choisie touchée de nouveau laisse l'événement sans étiquette (R13), et « + Nouvelle » ouvre une seconde feuille au-dessus de la première ([décision 0057](../../decisions/frontend/0057-ecran-pour-qui-et-etiquettes.md)) : un nom et une des huit couleurs, puis « Créer » ; l'étiquette créée est choisie sur l'événement, sans relire la page, pour garder le formulaire (R12). Les deux partenaires suppriment un événement partagé après confirmation (R9), ou depuis la liste du jour en glissant sa carte vers la gauche ([décision 0049](../../decisions/frontend/0049-suppression-par-glissement.md)) : la carte sort tout de suite et revient si l'API refuse. Chaque commande est une server action qui revalide le formulaire et l'identifiant (`services/calendar-event-commands.service.ts`). Un succès affiche un toast court, ferme la feuille et relit la page par `router.refresh()` ; comme `replaceState` passe par le routeur de Next, la relecture lit l'adresse courante et le jour choisi reste le même. Un refus suit le chemin des notes : connexion sur `UNAUTHORIZED`, fermeture et relecture sur `NOT_FOUND`, `FORBIDDEN` et `CONFLICT`.

L'onglet « Messages » (`src/app/(tabs)/messages/page.tsx`, module `apps/couple/web/src/modules/messaging/`) suit le même chemin. La page lit en parallèle le couple, la première page du fil (`loadFirstMessageFeedPage()`, 25 éléments, du plus récent au plus ancien, R5) et l'invitation du jour (`loadTodayPhotoPrompt()`), applique les renvois de l'accueil, puis `presentMessagesPage` : connexion sur `UNAUTHORIZED`, `/pairing` sur `MESSAGING_COUPLE_NOT_PAIRED`. Le fil est groupé par jour de Paris (« Aujourd'hui », « Hier », puis la date), chaque élément avec son heure de Paris ; les miens à droite en terre cuite, ceux de l'autre à gauche en sauge. « Voir les plus anciens » lit la page suivante par une server action, au curseur du dernier élément ([décision 0025](../../decisions/0025-pagination.md)). Une carte « C'est l'heure de la photo » s'affiche en haut tant que je n'ai pas répondu à l'invitation du jour : son heure, les minutes avant « en retard » comptées à la lecture de la page, et si l'autre a déjà envoyé la sienne (R8, R9).

Le composeur reste au-dessus de la barre d'onglets : quatre mots prêts envoyés d'un toucher, l'appareil photo, un champ « Un petit mot… » de 16 px validé par `createFlashMessageFormSchema(t)` (R2) et le bouton d'envoi. L'appareil photo s'ouvre par un champ fichier (`accept="image/*"`, `capture="environment"`) ; la PWA ne vérifie que le poids (10 Mo), jamais le type déclaré, qu'un iPhone peut donner en `image/heif` ou pas du tout : l'API lit le format dans les octets (R3). La photo passe par un aperçu plein écran (« Reprendre », « Envoyer »), puis part dans un `FormData` vers une server action qui revérifie le poids ; ouverte depuis la carte de l'invitation, elle répond à l'invitation (R8). Next refuse par défaut un corps de server action de plus de 1 Mo, et le proxy coupe un corps de plus de 10 Mo : `next.config.ts` relève les deux à 11 Mo. Un toucher sur mon mot ou ma photo ouvre une feuille « Retirer pour nous deux » ou « Garder » (R6) ; ceux de l'autre ne s'ouvrent pas.

Le navigateur ne parle jamais à l'API, photos comprises : une photo visible pointe vers le route handler `src/app/api/instant-photos/[instantPhotoId]/route.ts` (`WebRouterEnum.INSTANT_PHOTO_FILE`), qui lit le cookie de session, appelle `GetInstantPhotoFileUseCase` et renvoie les octets avec leur type et `Cache-Control: private, no-store` ; il répond 404 à un refus de l'API, 401 à une session refusée, et `proxy.ts` renvoie vers la connexion une demande sans cookie. Le service worker passe cette route en réseau seul : aucune photo du couple ne reste en cache après une déconnexion ([décision 0036](../../decisions/frontend/0036-lecture-des-donnees-par-la-page-serveur.md)). La photo du jour cachée de l'autre n'a pas d'adresse : la PWA montre un cadenas et « Envoie la tienne pour voir la sienne », sans jamais demander ses octets (R9).

L'accueil, l'onglet « Agenda », l'onglet « Messages » et l'onglet « Nous » (`src/app/(tabs)/couple/page.tsx`) partagent le layout du groupe `src/app/(tabs)/`, qui pose la barre d'onglets en bas de l'écran ([décision 0044](../../decisions/frontend/0044-navigation-par-onglets.md)). « Nous » lit le couple par `loadMyCouple()`, puis `presentCoupleOverviewPage` applique les renvois de l'accueil et donne la date de formation du couple, puis `presentTogetherTime` le nombre de jours passés ensemble et son équivalent en années, à partir des périodes ensemble du couple ([décision 0045](../../decisions/pairing/0045-periodes-ensemble-du-couple.md)) ; la carte « Étiquettes de l'agenda » porte `CalendarLabelsContainer` du module `agenda` (la page lit les étiquettes en parallèle du couple, `loadCalendarLabels()`, puis `presentCalendarLabelsCard` ; un refus de cette lecture n'affiche que l'avis de la carte, avec « Réessayer ») : chaque étiquette, son point et son nom, s'ouvre au toucher dans la feuille « Modifier l'étiquette » (nom, couleur, « Enregistrer »), d'où « Supprimer l'étiquette » demande une confirmation qui dit que ses événements restent, sans étiquette (R12, R14) ; un succès ferme la feuille et relit la page ; la carte « Notifications sur ce téléphone » porte `PushNotificationsContainer` du module `messaging` (R11 des messages : lu dans le navigateur après l'hydratation, puis « Activer les notifications » ou « Désactiver ») ; la carte « Ce téléphone » porte `SignOutContainer` du module `authentication`.

Le titre d'une note mène à sa page, `src/app/notes/[noteId]/page.tsx` (`WebRouterEnum.NOTE_EDITOR`) : `loadNote(noteId)` lit `GET /notes/:noteId`, puis le lieu où elle est (`GET /note-spaces/:space/contents`, l'espace tiré de sa visibilité), et `presentNotePage` renvoie vers l'accueil une note disparue ou privée de l'autre. Le retour mène au dossier de la note, ou à la racine de son espace, et porte son nom ; le « ⋯ » ouvre la même feuille qu'une ligne de l'écran, dont le sélecteur part de ce lieu. Une note supprimée depuis sa page renvoie vers ce lieu. Le titre s'y renomme. Le contenu s'y écrit à deux dans Tiptap (voir [l'édition à deux](../notes/collaboration.md#dans-la-pwa)). Une note d'un dossier IA porte sa fiche au-dessus de l'éditeur (R20 à R22) : chaque case et sa valeur, « Non trouvé » en italique, « corrigée » pour une valeur écrite à la main ; un toucher sur une case ouvre une feuille qui la corrige. « Mettre à jour » relance la recherche, grisé tant qu'elle tourne, absent hors d'un dossier IA (R25). En recherche, la fiche montre des `Skeleton` et la page se relit toutes les quatre secondes ; une fiche en doute montre « Lequel ? » dessous ; « La recherche n'a pas abouti » propose « Réessayer » ; au-delà du plafond du jour, la fiche le dit. Le pied « 2 sources · recherchée le 25 nov. » déplie les liens, ouverts dans un nouvel onglet. Les notes libres suivent sous « Nos notes ». Le lien vient de `resolveRoute` de `@cocooning/client-infrastructure`, avec une origine vide.

## La session dans la PWA

| Élément | Rôle |
|---|---|
| Cookie `SESSION_COOKIE_NAME` | Posé par la server action après la connexion : `HttpOnly`, `Secure` en production, `SameSite=Lax`, `path=/`, expiré à `sessionExpiresAt` ([décision 0034](../../decisions/0034-session-revocable.md)). Le jeton n'apparaît ni dans la réponse de l'action ni dans le code client |
| `src/proxy.ts` | Renvoie vers `WebRouterEnum.ACCOUNT_SIGN_IN` toute page ou route handler (`app/api/**`) demandé sans cookie, sauf l'écran de connexion et `WebRouterEnum.OFFLINE`. Le `matcher` exclut les fichiers de la PWA, demandés sans cookie (manifeste, icônes, service worker). Il ne vérifie que la présence du cookie : le garde de session de l'API vérifie le jeton à chaque appel |
| `src/env/server.ts` | `API_URL`, `API_TIMEOUT_MS` et `NOTES_COLLABORATION_URL` (adresse du canal temps réel, passée par la page au navigateur), validés au démarrage du serveur par `src/instrumentation.ts`, jamais exposés au navigateur (`server-only`) |

Une page qui reçoit `UNAUTHORIZED` renvoie vers la connexion. « Se déconnecter » (`SignOutContainer`, sur l'accueil et `/pairing`) appelle `DELETE /authentication/session` avec la session : l'API ferme les sessions de tous les appareils, puis l'action retire le cookie de ce navigateur. La fabrique `createAuthenticationModule` reçoit donc elle aussi `getSessionToken`, que seule la déconnexion lit ; la connexion part sans cookie ([décision 0042](../../decisions/frontend/0042-fournisseur-de-session-des-fabriques.md)).

## Les erreurs

`httpRequest` ne lève jamais. Un échec devient une `ApiError` `{ code, message, backendCode }` :

| Cas | `code` |
|---|---|
| Réseau coupé, délai dépassé | `NETWORK_ERROR` |
| Réponse de succès illisible ou hors contrat | `INVALID_RESPONSE` |
| 400 ou 422 | `VALIDATION_ERROR` |
| 401 | `UNAUTHORIZED` |
| 403 | `FORBIDDEN` |
| 404 | `NOT_FOUND` |
| 409 | `CONFLICT` |
| Autre statut | `UNKNOWN` |

`backendCode` reprend le `code` du corps d'erreur de l'API (par exemple `PAIRING_INVITATION_CODE_INVALID`), ou `null`. Le container l'affiche en toast : un titre traduit propre à l'action, et en description `describeApiResultError(error, t)` (`apps/couple/web/src/shared/application/api-result/`), qui traduit `apiErrors.<backendCode>`, sinon `apiErrors.<code>`, sinon garde le message de l'API ([décision 0010](../../decisions/frontend/0010-affichage-erreur-serveur.md)). Les clés vivent dans le namespace de l'écran (`src/i18n/locales/fr/<module>/<écran>.json`), une par code de la liste `<ÉCRAN>_SCREEN_ERROR_CODES` du dossier `data/` du module ([décision 0037](../../decisions/frontend/0037-traductions-des-erreurs-par-ecran.md)).
